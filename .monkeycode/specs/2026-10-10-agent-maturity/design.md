# E 系设计要点（缓存经济学 / 事件流 / 子代理 / 护栏）

> 状态：E1–E5 全部完成（2026-10-10，c1009c23）。这里是**做决定的地方**——
> 每条都写明「为什么这样做、为什么不做另一种」。

## E1 缓存经济学

- **前缀缓存的物理约束**：提供商按 token 序列做前缀缓存，任何位置的内容变化会让
  「该变化点之后」全部 miss。因此 systemPrompt 的**行序就是缓存契约**：
  静态段（身份 / 技能 / 引导）在前，高频动态段（readLog——每读一个文件就多一行）
  在**最末尾**。测试用「readLog 行之后不允许再有任何行」钉死这条。
- **不做 price 换算**：BYO 端点的价格表不存在统一来源，显示「缓存命中 x/y（z%）」
  比拍脑袋的美元数字诚实。
- **usage 口径统一为 prompt ⊇ cached**：Anthropic 的 input_tokens 不含缓存部分，
  解析时把 cache_read + cache_creation 并进 prompt——三种方言在统计层可比。
- **tools 顺序**：单次 runAgentTurn 内是同一数组引用（天然冻结）；跨轮由纯函数
  listToolsForMode 保证（已有测试钉死顺序）。运行时兜底只做开发期告警
  （toolOrderSignature 比对），不引入任何能改变顺序的逻辑。

## E2 护栏与压缩自动化

- **重复调用只 nudge 不阻断**：模型重试有时是合理的（文件被外部改动）。nudge 放
  **轮末**（与预算预警同位置）——插在 tool_calls 与 tool 消息之间会破坏 OpenAI
  协议的配对结构。
- **签名键序稳定化**：{a:1,b:2} 与 {b:2,a:1} 是同一参数，不做稳定化会漏检。
- **自动压缩不在发送路径上**：发送前压缩会有「压缩替换消息」与「发送读消息」的
  时序竞态（React 闭包读旧值）。改为**空闲场景**的 effect 触发：85% + 未发送 +
  未压缩中 → 静默执行；失败等下次消息增长再试（同一消息条数只尝试一次，防死循环）。
- **70/85 双阈值**：70% 提示条给用户主动权（一键压缩 / 可忽略），85% 静默兜底。
  设置项 autoCompact 默认开、可关——关掉后 70% 提示仍在（只失去自动执行）。

## E3 子代理体系

- **防递归在名字层，不在解析层**：`parseAgentMarkdown` 的 tools 与
  SUBAGENT_TOOL_NAMES 求交集（写 run_subagent 静默丢弃）；SUBAGENT_TOOL_NAMES
  永远不含 run_subagent——两层都结构性，不靠"记得别给"。
- **每轮直读档案**：与 skills / hooks 同款——agent 刚建的档案下一轮就能用。
- **并发上限 2**：手机端同时两条独立模型流是上限（网络与限流）；
  mapWithConcurrency 保序返回，单路失败不拖垮整批（该路段如实标注）。
- **不做 per-agent 模型**：BYO 端点定位下统一走活动配置（刻意的简化）。

## E4 会话事件流

- **只写不回读**：jsonl 是审计旁路，绝不参与消息渲染——写失败静默（事件流不能
  成为消息链路的故障源）。UI 热数据仍以 AsyncStorage 消息为准。
- **不另起分支树**（二期裁决）：消息级分叉/切换已由 branchTree + sessionBranches
  提供（撤回尾段归档 + 任意点切换）；事件流只记录事实。
- **追加 = 读改写（如实登记）**：SAF store 无 append 原语；事件行很小（~200B），
  千条级 200KB 可接受；SESSION_EVENTS_MAX_BYTES（512KB）到顶停止追加并返回 null
  （可见的失败胜过静默增长）。

## E5 Git 观感

- **diff 走 text 解析**：request 层加 accept + parse='text' 两个可选参数，默认行为
  逐字节不变（已有测试钉着）。
- **PR 是写操作**：先确认（head → base 说清）后创建；head === base 在 UI 层拦截
  （不发必失败的请求）；失败按错误码映射（复用 describeError）。
- **截断形状复用**：diff 与 shell/MCP 同款「头 3/4 + 尾 1/4」——diff 的要点常在
  尾部 hunk 与文件统计里。

## 对任务书的三处修正（防跑偏记录）

1. 「自动压缩缺失但 80% 已有」不准确——80% 触发的是**记忆总结**（写记忆库，
   不替换消息），会话压缩（applyCompaction）此前只有手动按钮。
2. 「E4 二期消息级分叉」——已完整存在（撤回即归档为分支、BranchForkRow 切换），
   不重做。
3. `shouldCompact`（4MB）与 `shouldAutoCompact` 都未接线；E2 接的是后者（85%），
   前者（4MB 体积线）维持手动触发语义。
