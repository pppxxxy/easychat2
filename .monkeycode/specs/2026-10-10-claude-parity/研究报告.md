### P0-7 接线设计（2026-10-10 核实后的结论，下半已按此落地于 `39ec5f5`）

**接线点选在 `src/network/api.js` 的 `streamChatCompletion`**，不是 `useChatSend`：
`useChatSend` 不直接调它（聊天走 `agent/loop.js` 的 `runAgentTurn`，群聊/总结/压缩各有一条），
逐处加壳会漏。`streamChatCompletion` 是所有在线请求的**唯一收口**。

**但它当时不是可循环的薄包装**：241–687 行是单体内联实现（解析配置 → 构造 payload →
内联 XHR → 流式解析），没有可供重试调用的单次函数。因此接线的前提是一次**重构**：
把 XHR 主体抽成 `requestOnce(messages, options, { model })`，`streamChatCompletion` 变成
「按链循环调用 requestOnce」的薄层。**这是重构而不是加壳**（抽取后逐字行为不变，
既有 2209 条测试全绿），按单独一批落地并单独评审。

「是否已产出」的判定也在这一层做：包装调用方传入的 `onChunk`/`onReasoning` 打标，
一旦有过回调就禁止降级（`shouldFallback({ emitted })` 已按此语义实现并有测试）。

配置入口（API 配置卡片加「降级模型」输入 + 存储归一化 + 中英词条）与接线**同批**做了——否则会先落地一个「设了不生效」的死开关。落地时的三处补充（设计时未写、实现时按证据定的）：

1. **每次尝试按该模型重算三项**（能力 `capabilitiesForModel`、`max_tokens`、`contextWindow` 裁剪）：降级模型的能力条目是**它自己的**，沿用主模型的窗口/预算属于静默串味（`tests/apiFallbackChain.test.mjs` 有钉住）；
2. **提示面覆盖三条聊天路径**：单聊（`requestReply`）、群聊发言（`runTurnSpeakers`）、群像（`runEnsemble`）都接 `onModelFallback`；群聊内部的选人/简介/开场这类辅助请求不接（不是用户可见回复，接了只是噪声）；
3. **中间失败仍各记一条诊断日志**：一次降级就是一次真实失败，如实记录而不是抹掉。

## 0. 结论摘要

### 0.1 一句话结论

easychat2 的 agent/工作区在「安全与诚实边界」上**明显强于** Claude Code 的移动端可移植部分（只读白名单子代理、deny 最高优先、MCP 三档硬禁、声明式钩子、缓存前缀契约、能力说明卡片如实告知限制），**主要差距集中在三处**：
1. **能力已建但入口缺失**（文件快照恢复、事件流回读）；
2. **研究型工具的缺口**（无 `web_fetch` 抓正文、无 grep/glob 检索）；
3. **配置层级与调度面**（无工作区级设置、无用户级资产 scope、无显式缓存断点）。

### 0.3 已经对齐良好、**不必重复投入**的部分

- **权限引擎**：`{effect,tool,match,scope}` 形状已覆盖 Claude Code 的 `Tool(specifier)` 主用法（tool 级 + 命令词边界前缀 + 路径 glob + deny 最高优先 + 会话/永久作用域）。Claude Code 的 `Tool(param:value)` 参数级匹配是唯一增量。

- **子代理防递归**：名字白名单 + 不接触注册表（结构性保证），比 Claude Code 的「工具列表 + 深度上限」更难绕过。
- **缓存前缀契约**：readLog 行置尾 + tools 顺序冻结 + 三方言 usage 解析（E1）已等价 Claude Code 的 cache 观测面。
- **工作区记忆自我演进**：AGENTS.md 每轮直读 + agent 可写 + 8KB 截断（T2）已覆盖 CLAUDE.md 的核心价值。
- **技能/命令渐进披露**：`.easychat/skills/<name>/SKILL.md` + `allowed-tools`（软约束）+ 命令 `$ARGUMENTS`，与 Claude Code 的 skills/commands 同构（Claude Code 已把 commands 并入 skills）。
- **诚实边界**：能力说明卡片 10 条限制（无 pip / 外部根无 shell / 终端无流式 / 本地模型不参与工具循环…）——Claude Code 文档没有等价物，这是 easychat2 的优势。

## 1. 「四月泄露源码」的核实结果与调研口径

### 1.1 本机网络事实

| 目标 | 结果 |
|---|---|
| `code.claude.com`（官方文档） | ✅ 可达（注意：`/docs/en/<page>` 只返回导航壳，必须用 `/docs/en/<page>.md` 才拿到完整正文） |
| `registry.npmjs.org` | ✅ 可达 |
| `github.com` / `raw.githubusercontent.com` / `cdn.jsdelivr.net`（回源 raw） | ❌ DNS 不通（`getaddrinfo ENOENT` / `fetch failed`） |
| 搜索引擎（DuckDuckGo/Bing HTML） | ❌ 不可达；`web_search` 工具亦无 API key |

→ **无法核实那次泄露的具体内容**（GitHub 上的逆向分析仓库、社区报道都取不到）。

### 1.2 能核实到的时间线（这解释了「四月泄露源码」）

- npm 上 `@anthropic-ai/claude-code` **当前版本 2.1.296 已是原生二进制分发**：`bin/claude.exe`、`fileCount: 7`、`unpackedSize: 189 KB`，另有 8 个平台专属 `optionalDependencies`（`@anthropic-ai/claude-code-{linux-x64,win32-x64,darwin-arm64,…}`）。
- 官方 What's New **Week 16（2026-04-13 ~ 04-17，v2.1.105–113）** 明确写着：「**the CLI moves to native binaries**」。
- 时间线吻合：**2026 年 4 月正是从「npm 包内是可读的（压缩过的）JS bundle」切换为「原生二进制」的时点**。此前任何人都能从 npm 拉到那份 JS 并反编译/分析（社区所谓「泄露源码」即源于此）；切换之后不再有 JS 源码可看。
- 结论：所谓「4 月泄露的源码」= **原生二进制化之前那代 JS bundle 的公开可分析状态**。它反映的是 2026-04 之前的实现；而 Claude Code 此后又发布了 20+ 周的迭代（见 §1.3），因此**即使拿到那份源码，用来做「还能补什么」的判断也已经过时**——官方文档才是当前能力面的权威来源。

## 3. 建议补充的功能（逐条落地要点）

> 工作量按「熟悉本仓库的助手」估；风险标注安全/兼容性影响；依赖标注前置项。

### P0-1 文件快照「查看 + 恢复」入口（J1 二期）

- **做什么**：文件面板（或工作区设置层）新增「文件历史」入口：按路径列出快照（时间、来源、大小、是否可恢复）→ 预览与当前内容的行级 diff（复用 `lineDiff.js` + `DiffView.js`）→ 一键恢复（复用 `restoreFileHistory`，恢复前自动再快照当前）。
- **为什么**：J1 已实现记录与恢复**能力**，但 `listFileHistory`/`readFileHistoryEntry`/`restoreFileHistory` **只被测试引用**——用户与 agent 都无法触达，等于「后悔药做了但没上架」。这是本报告发现的最高价值缺口。
- **落地**：`src/workspace/screen/FilesPanel.js`（或新 `FileHistorySheet.js`）+ 复用 `fileHistory.js` 现有纯 IO；入口可在文件预览页「⋯」菜单加「历史版本」，也可在工作区设置层 actionRows 加一行（现 actionRows 有 import/export/events/history/env，其中 `history` 是「打开文件面板」）。
- **风险**：恢复是覆盖写 → 必须走「恢复前先快照」既有语义（已实现）；建议恢复也**写进 E4 事件流**（审计）。
- **量**：1–2 天（UI 为主）。

### P0-2 `web_fetch` 工具（抓网页正文）

- **做什么**：新增工具 `web_fetch({url, maxChars?})`：优先走搜索 provider 的 extract 能力（AnySearch `/v1/extract`、Tavily extract 等），无 extract 时退化为 XHR 拉取 + 正文抽取（去标签/压缩空白）；结果用 `<external_fetch_data>` 包裹并注明「外部不可信数据」；域名允许列表门控；结果截断（建议 16KB，与工具结果上限一致）。
- **为什么**：现在只有 `web_search`（snippet 约 160 字），研究型任务（「查某库的 API 用法」「读这个 issue」）拿不到正文；子代理也只能靠搜索 snippet 拼凑。
- **落地**：新建 `src/chat/webFetchTool.js`（或并入 `chatTools.js`）；复用 `src/plugins/providers.js` 的 provider 抽象 + `network/vendorHttp.js`（缓存/限流/重试已有：60s TTL、20 次/分、1 次重试）；与 `web_search` 同开关（`chatOptions.chatTools`）但**独立工具名**，便于权限规则分别管。
- **风险**：数据外发（同 web_search，已有开关语义）；SSRF（需禁 `file://`/`localhost`/内网段——建议只允许 https + 公网）。
- **量**：1–2 天（含测试：URL 校验、截断、不可信包裹、域名白名单）。

### P0-3 `search_workspace_files` 工具（沙盒内 grep/glob）

- **做什么**：`search_workspace_files({pattern, path?, glob?, maxResults?, contextLines?})`：遍历沙盒文本文件（复用 `listWorkspaceFiles` + `isTextWorkspaceFile`），正则/子串匹配，返回 `文件:行号: 行内容`（含可选上下文行），结果上限（建议 100 命中 / 16KB）。
- **为什么**：Claude Code 的 `Grep` 是其最高频工具之一；easychat2 的子代理只有 `list` + `read`，为找一个符号要逐个文件读 → 直接放大 token 与轮次。这是**成本与效率双收益**。
- **落地**：`src/workspace/toolDefs/searchTool.js`（readOnly，read/write 模式可见）+ 纯函数 `src/workspace/search.js`（Node 直测：正则编译、glob 过滤、上限截断、二进制跳过）。注意 2000 文件 / 1MB 读取上限 → 建议逐文件流式扫描 + 单文件命中上限。
- **风险**：性能（大工作区）→ 加「扫描文件数上限 + 超时（复用工具超时）」；ReDoS → 限制正则复杂度或只允许字面量+简单通配（建议先做「字面量 + 可选大小写」最稳，正则作为二期）。
- **量**：1 天。

### P0-4 修 `timeoutMs` 在注册聚合层丢失（Bug）

- **做什么**：`SLOW_TOOL_TIMEOUTS` 补 `run_subagent: 300000`、`run_remote_build: 60000`、`get_build_log: 90000`；或改为「优先读工具定义自带 `timeoutMs`，映射表只作覆盖」。
- **为什么**：三个工具定义里声明了长超时，注册聚合只透传 shell/python 两项 → 实际都退到 15000ms。子代理多轮模型请求、云构建触发与日志下载**必然超过 15s**，会被 `runTool` 判为「工具执行超时」并回喂错误。现有测试只做源码字符串断言（`tests/subagent.test.mjs:258,300`），门禁全绿。
- **落地**：`src/workspace/tools.js:53-56,95-104` + **补行为测试**（断言注册表实例的 `timeoutMs`，而非源码字符串）。
- **风险**：无（纯修复）。
- **量**：2 小时（含测试）。

### P0-5 压缩自定义关注点 + 修阈值不一致

- **做什么**：① `/compact <关注点>` 把用户指令拼进 `COMPACTION_SYSTEM_PROMPT`（如「重点保留 API 变更与未决问题」）；② 统一压缩阈值：`AUTO_COMPACT_RATIO` 与实际使用值二选一（建议设置项 `chatOptions.autoCompactRatio`，默认 0.85，常量与 `memorySummary` 的 0.8 各自命名区分）；③（可选）按模型窗口而非固定比例（`autoCompactWindow` 等价物）。
- **为什么**：压缩摘要质量直接决定长会话可用性；固定三段式在「正在调 bug」时会丢关键细节。阈值不一致是**已存在的隐性 bug**。
- **落地**：`src/chat/compaction.js:25-32`（提示词加参数）+ `ChatScreen.js:1495-1536`（解析 `/compact` 参数）+ `contextUsage.js:15` 与 `ChatScreen.js:1574` 统一。
- **风险**：低（提示词变更需真机看效果）。
- **量**：半天。

### P0-6 权限规则加 `ask` 显式档

- **做什么**：`PERMISSION_EFFECTS` 增 `ask`；求值顺序 `deny → ask → allow`（ask 命中即弹框，即使存在更宽的 allow）；`normalizePermissionRule`/`evaluatePermissionRules`/`describePermissionRule` 同步；弹框新增「这个工具每次都问」选项（若按钮数受限，可在设置页手写规则）。
- **为什么**：现在只有 allow/deny，用户无法表达「`run_shell` 我可以让 `git status` 免问，但 `rm` 类必须每次问」——更宽的 allow 会静默放行。Claude Code 的三态是权限系统的必要表达力。
- **落地**：`src/agent/permissions.js:21,135-142`（纯函数，Node 直测）+ `src/chat/toolApprovalFlow.js` + 设置层规则列表（`WorkspaceSettingsSheet.js:350-377`）。
- **风险**：安全方向正确（更严），但需保证 `ask` 不被 hooks 的 `extraRules` 意外降级。
- **量**：半天。

### P0-7 `fallbackModels` 模型降级链

- **做什么**：配置 `fallbackModels: [configId|modelId, …]`（最多 3）；请求在 **429 / 5xx / 超时 / 网络错误** 时按序换下一个重试一次；流式已开始输出后不回退（避免半截回复重复）；UI 在 API 配置卡提供「降级链」编辑。
- **为什么**：BYO 端点（自建中转、第三方聚合）抖动是常态；现在只能整轮失败，用户手动重发。Claude Code 有 `fallbackModel`（最多 3 个按序），是其可用性设计的关键一环。且 easychat2 已有「本地→在线一次性回退」的骨架（`network/modelProvider.js`）。
- **落地**：`src/network/modelProvider.js`（扩展为 N 级链）+ `src/network/api.js`（错误分类已具 `code`，可判定可重试）+ 设置页 API 卡。
- **风险**：成本（可能多花钱）；必须**可见**（气泡/统计标注「已降级到 X」），不能静默。
- **量**：1 天。

### P0-8 钩子事件面扩展 + hooks 面板

- **做什么**：① 事件扩展（按价值序）：`before_tool`（**泛化 PreToolUse**：按工具名 + 参数匹配，可 deny，覆盖 write/edit/exec 而不只 shell）、`before_prompt`（UserPromptSubmit：注入额外上下文/拦截）、`after_turn`（Stop）、`before_compact`（PreCompact）、`session_start`/`session_end`；② matcher 支持 `|` 列表与正则；③ 新增动作 `inject_context`（把 message 注入下一轮 system/user 上下文，而不只是工具结果）；④ 设置层 hooks 行从「只显示文件路径」升级为**列表 + 校验 + 安装示例**（与 skills/commands 一致）。
- **为什么**：现在 `before_shell` 只管 shell —— 「禁止 agent 改 `.easychat/hooks.json`」「改完某目录必须跑测试」这类约束无处安放；且 hooks 完全不可见（设置层只有一行文字提示），用户写了也不确定生效没有。
- **落地**：`src/workspace/hooks.js`（事件表 + 归一化 + 求值，纯函数）+ `chat/useChatSend.js` 与 `ChatPanel.js` 注入点 + `WorkspaceSettingsSheet.js` hooks 段。
- **风险**：**不要越界**——保持声明式、无脚本执行（既有裁决正确：RN 进程内 eval 能触达全部原生桥）。事件变多后需注意「每轮直读 hooks.json」的成本（一次沙盒 IO，可忽略）。
- **量**：2 天。

### P1-1 显式缓存断点（Anthropic `cache_control`）+ TTL 配置

- **做什么**：anthropic 协议体里给 system 尾与「历史稳定前缀」打 `cache_control: {type:'ephemeral'}`（最多 4 个断点），并加配置 `promptCacheTtl`（5m/1h，Anthropic 支持 `ttl`）；OpenAI 系保持自动缓存（无需断点）。
- **为什么**：E1 已把前缀做稳定并观测命中率，但**没有主动打标**——Anthropic 需要显式断点才会缓存；这是「已铺好路、只差一步」的成本/延迟收益。
- **落地**：`src/apiProtocols/body.js:57-68`（anthropic 分支）+ `messages.js`（`toAnthropicRequest` 保留结构）+ 设置项。
- **风险**：断点位置不当会降低命中；需用 E1 的命中率指标验证（已有观测，可回归）。
- **量**：1–2 天。

### P1-2 工作区级设置 `.easychat/settings.json`

- **做什么**：新增工作区级设置文件（模式、shell/python 开关、压缩阈值、模型/配置、思考强度、语言），合并规则「工作区 > 全局」；设置页显示**生效来源**（全局/工作区/默认）；随工作区备份/迁移（现有备份是否含 `.easychat` 需核实）。
- **为什么**：多项目用户（不同仓库要不同模式与模型）现在只能每次手动切；工作区不能自治，也让「工作区」这个概念不完整。Claude Code 的 project/local settings 是其最实用的设计之一。
- **落地**：`src/workspace/settings.js`（归一化 + 合并）+ `src/storage/workspace.js`（读工作区文件）+ 各消费点（`useWorkspaceSettings`、`useChatSend` 读模式处）。
- **风险**：**安全**——工作区文件可能来自导入的仓库（不可信）；必须遵守 Claude Code 的教训：**工作区级只允许「收紧」类设置生效，放宽类（模式提到 write、开启 shell）必须显式确认**（与 workspace trust 等价）。建议：`.easychat/settings.json` 里放宽类字段默认忽略，需用户在设置页点「信任此工作区」后才生效。
- **量**：2–3 天。

### P1-3 用户级资产 scope（跨工作区共享）

- **做什么**：新增应用级资产目录（如 `<documentDirectory>/easychat-global/{skills,commands,agents,rules}`），加载顺序「工作区级覆盖应用级」；设置层显示来源徽标；提供「从工作区提升到全局」一键操作。
- **为什么**：常用技能/命令/分身现在每个工作区都要重装（示例安装是幂等的，但用户自写的资产要手动复制）。
- **落地**：`skills.js`/`commands.js`/`agents.js` 的「发现」函数改为「两处扫描 + 覆盖」；`FilesPanel` 的技能安装入口扩展。
- **风险**：低；注意 20/20/12 的清单上限需要合并后统一计算。
- **量**：2 天。

### P1-4 记忆：`rules/*.md`（`paths` 门控）+ 快速记忆入口 + `@import`

- **做什么**：① `.easychat/rules/*.md` 支持 frontmatter `paths`（glob），只在相关路径被读/写时注入；② 输入框 `#` 前缀 = 追加一条到 AGENTS.md（带确认预览）；③ AGENTS.md 支持 `@path` 导入（限沙盒内、跳代码块、深度 ≤4、总预算仍 8KB）。
- **为什么**：8KB 是硬预算，大项目的约定放不下；「按路径生效」让预算花在相关处。`#` 快速记忆把「记一条」从「让 agent 改文件」降到一次输入。Claude Code 的 rules + `@import` + `#` 是记忆体系里最实用的三件套。
- **落地**：`src/workspace/memory.js`（导入解析 + 预算分配）+ 新 `src/workspace/rules.js` + `chat.js` 注入顺序 + `ChatPanel.js` 输入拦截。
- **风险**：预算分配需明确（建议：AGENTS.md 8KB + rules 合计 8KB，或统一 12KB 并如实截断提示）。
- **量**：2 天。

### P1-5 子代理：`@` 提及调用 + 分身记忆 + 过程可见性

- **做什么**：① 输入框 `@` 选择器列出 `.easychat/agents/*`（与群聊提及共用 UI 骨架 `MentionPickerModal`），选中即直接委派（不走模型判断）；② `.easychat/agent-memory/<name>/MEMORY.md`（启动注入前 200 行 / 25KB，分身可写）；③ 分身过程写入 E4 事件流并加 `agent` 维度，ChatPanel 折叠展示。
- **为什么**：现在分身只能靠模型「想起来用」，用户无法点名；研究型分身每次都从零开始；过程不可见导致「它到底查了什么」无法追溯。
- **落地**：`agents.js`（+memory 路径与解析）+ `subagentTool.js`（显式调用入口）+ `ChatPanel.js`（提及条）+ `sessionEvents.js`（agent 维度）。
- **风险**：低；记忆注入要计入上下文预算。
- **量**：2–3 天。
- **注**：`model`/`effort` 字段见 §5（需裁决）。

### P1-6 `ask_user` 结构化提问工具

- **做什么**：`ask_user({question, options:[…], multi?})` 工具：模型在信息不足时向用户提问（选项式，可多选），答案以工具结果回喂；UI 用自绘 Modal（Android Alert 3 按钮不够）。
- **为什么**：现在模型只能「猜」或「在正文里问一句然后停下」；Claude Code 的 `AskUserQuestion` 显著减少无效往返（尤其权限/偏好类问题）。
- **落地**：新工具（readOnly 但需 UI 钩子，类似 `requiresConfirmation` 的审批通路，可复用 `onToolApproval` 的接线方式）+ 新 Modal + i18n。
- **风险**：**无 UI 时必须拒绝**（沿用「没有审批钩子 = 拒绝」的既有纪律，headless/定时任务场景下该工具应直接返回「当前环境无法提问」）。
- **量**：1–2 天。

### P1-7 `@` 提及文件/技能/命令注入上下文

- **做什么**：工作区输入框 `@` 可提及沙盒文件（注入该文件内容或路径+摘要）、技能、命令；与 P1-5 的 `@agent` 共用一个选择器（分类 tab）。
- **为什么**：Claude Code 的 `@file` 是最常用的上下文注入方式；easychat2 现在只能靠模型自己 `read`（多一轮 + 可能读错文件）。
- **落地**：`ChatPanel.js` 输入区 + `readLog.js` 复用 + 注入预算控制（提及文件内容也走 16KB/工具结果同口径截断）。
- **风险**：注入大文件会挤爆上下文 → 必须截断 + 明确提示「已截断，可让助手用 offset 续读」。
- **量**：1–2 天（与 P1-5 合并做更省）。

### P1-8 后台长命令（`run_in_background` + 增量读输出 + kill）

- **做什么**：`run_shell` 增参数 `background: true` → 命令在原生侧后台跑、输出写沙盒内日志文件（`.easychat/jobs/<id>.log`）；新增 `read_job_output({id, offset})` 与 `kill_job({id})`；设置层/对话面板显示运行中的后台任务。
- **为什么**：Android 上跑 `pip`（无）、`python` 长任务、`curl` 大文件、测试套件都受 30s 超时限制；Claude Code 的 `Ctrl+B` + Monitor 正是为此。**这是移动端最实用的能力缺口之一**。
- **落地**：`plugins/shellExecutor/android/ShellExecutorModule.kt` 需扩展（后台进程 + 输出重定向到文件 + kill by id）——**原生改动，本地无法编译验证**（AGENTS 记录：只能靠 CI Gradle 或真机 prebuild）；JS 侧 `shell.js` + 新工具 + 日志读取。
- **风险**：① 与「**不做后台自动执行任务**」裁决的边界——本项是「用户/agent 显式发起的单条命令后台化 + 用户可见 + 可 kill」，与「无人值守自动跑 agent 任务」不同；**建议先请用户裁决**。② 后台进程与 App 生命周期（App 被杀后残留进程）；③ 电量与 Doze。
- **量**：3–4 天（含原生 + 真机验证）。

### P1-9 MCP：`resources`/`prompts` + 工作区级 `.easychat/mcp.json` + 工具检索

- **做什么**：① 客户端补 `resources/list`/`resources/read`（暴露为只读工具）与 `prompts/list`/`prompts/get`（作为斜杠命令来源）；② 支持工作区级 `.easychat/mcp.json`（与全局合并，同名工作区优先），便于随工作区迁移/备份；③ 服务器数/工具数超阈值时改为「检索式暴露」（`search_mcp_tools` 先检索再注册相关工具）。
- **为什么**：① 生态里不少 MCP 服务器主要提供 resources/prompts；② 工作区自治（与 P1-2 同源）；③ 工具多了会持续吃上下文（Claude Code 专门做了 MCP tool search）。
- **落地**：`src/mcp/client.js`（新方法）+ `mcpTools.js`（注册策略）+ `storage/settings/mcpServers.js`（作用域合并）。
- **风险**：③ 改变了「不暴露即不可达」的既有安全模型 → 检索到的工具仍必须过 `classifyMcpTool` 与执行层复查（既有双保险不能绕）。
- **量**：3–5 天。

### P1-10 外发型工具域名允许列表 + 「数据外发清单」UI

- **做什么**：① 统一「外发门控」：`web_search`/`web_fetch`/MCP/GitHub/云构建/自定义 URL 下载 各自的域名集合集中登记，支持用户允许/拒绝（默认沿用现状，但**可见**）；② 能力说明卡片增加「数据外发清单」一节：哪些功能会把什么数据发到哪里（搜索词、URL、代码片段、工作区文件）。
- **为什么**：隐私是 easychat2 的既有价值观（`chatTools` 默认关的理由就是「数据外发」；能力卡片已有 githubImport 等 10 条边界）。但**没有集中视图**，用户很难回答「这个 App 到底会往外发什么」。Claude Code 的 sandbox network allowlist + credentials 遮蔽是同类思路（其默认「无网络直连」在移动端无法照搬，但「清单 + 白名单」可以）。
- **落地**：新 `src/workspace/egress.js`（域名集合 + 判定纯函数）+ 各外发点接入 + 卡片/设置页展示。
- **风险**：低（不改默认行为，先做「可见 + 可关」）。
- **量**：2 天。

### P1-11 保留期设置 + 明文存储提示 + 审计文件保护

- **做什么**：① 设置项：事件流 / 文件快照 / 回滚基线的保留天数与条数（现在分别是 512KB 到顶、200 条、3 份，均硬编码）；② 明示「这些文件是明文，落在工作区目录里」；③ 把 `.easychat/sessions/`、`.easychat/file-history/`、`.easychat/rollback/` 纳入**默认 deny 写入**（agent 不得覆盖审计与快照文件；用户仍可在文件面板手动删）。
- **为什么**：① 体积与隐私控制；② 诚实边界（Claude Code 明确警告转录明文、OS 权限是唯一保护）；③ **审计完整性**：现在 `write_workspace_file` 可以覆盖事件流/快照（T6 只论证了 hooks.json「只能收紧」，没覆盖这两个），等于审计可被 agent 抹掉。
- **落地**：`sessionEvents.js`/`fileHistory.js`/`rollbackBaseline.js`（保留期参数）+ `hooks.js` 或权限默认规则（审计路径 deny）+ 设置层。
- **风险**：③ 需确认不破坏既有流程（事件流是旁路、失败静默；快照由工具内部写，不经 `write_workspace_file`，因此 deny 规则不影响内部写）。
- **量**：1 天。

### P2-1 统一检查点回退（消息 + 文件联动）｜❗需重新评估「缓」裁决

- **做什么**：在分支切换/撤回时，提供「同时把工作区文件恢复到该时点」选项（用 file-history 的时间戳 + E4 事件流时间线关联；不精确时如实提示「只能按时间近似恢复」）。
- **为什么**：Claude Code 的 `/rewind` 是「对话 + 文件」一起回退；easychat2 两者独立，用户要手动做两件事且难以对齐时点。
- **既有裁决**：J 系把「多维度恢复合并菜单」裁为「缓」（`checkpoint-resume/tasklist.md:88`）。本报告建议重新评估的理由：P0-1 落地后 file-history 已有 UI，联动成本显著下降；且事件流（E4）提供了时间线锚点。
- **风险**：时间关联不精确会造成「以为恢复了其实没对齐」→ 必须**如实标注不确定性**（沿用仓库「不说假话」纪律）。
- **量**：3–5 天。

### P2-2 MCP 服务器模式（把工作区工具暴露给外部 MCP 客户端）

- **做什么**：新增「作为 MCP 服务器」开关：在本机 HTTP 端点暴露 easychat2 的工作区工具（只读子集起步），供桌面 Claude Code / 其他 MCP 客户端连接，实现「手机上的工作区被桌面 agent 操作」。
- **为什么**：与已有 `plugins/localApiServer`（模型侧 OpenAI 兼容服务）同思路的**能力侧**延伸；差异化强（Claude Code 的 `claude mcp serve` 是同类）。
- **风险**：**鉴权**——现有本地 API 服务「零鉴权、绑 127.0.0.1」已被登记为加固项（`审查待办.md:1821`）；本项必须先做 token 鉴权 + 只读白名单 + 明确的能力边界提示，否则不能上。
- **量**：3–5 天。

### P2-3 `consult_advisor` / 子代理模型选择｜❗需裁决

- **做什么**：允许把「某个子任务」或「子代理档案」指定到另一个（更强/更便宜）的 API 配置或模型；或提供 `consult_advisor` 工具（把当前对话摘要交给指定模型征求意见）。
- **既有裁决**：E3 明确「**不做 per-agent 模型**（BYO 端点定位下统一走活动配置）」（`agent-maturity/design.md:40`；`agents.js:15`）。**本报告不推翻该裁决**，只指出两个新证据：① 研究型子任务（翻文件找答案）用便宜快模型即可，成本可降一个量级；② 「advisor」是**质量**手段（关键节点请强模型复核），与「日常统一模型」不矛盾。
- **建议**：若用户认可，最小实现是「子代理可选一个**更便宜**的配置」（收窄用途），而不是「任意 per-agent 模型」。
- **量**：2–3 天。

### P2-4 成本估算（可选、用户自填单价）｜❗需裁决

- **既有裁决**：E1 明确「**不做价格换算**（BYO 端点无统一价格表）」（`agent-maturity/tasklist.md:44-45`）。本报告同意「内置价格表不可行」，但建议一个**不违反原意**的变体：用户可**自填**每个 API 配置的单价（input/output/cacheRead/cacheWrite），统计页按填写的价格显示估算金额，未填则仍只显示 token。这样既没有「猜价格」，又给需要的人成本可见性。
- **量**：1 天。

### P2-5 技能/命令的声明面补齐

- **做什么**：技能 frontmatter 增 `model`/`effort`/`paths`/`context: fork`(+`agent`)/`hooks`/`disable-model-invocation`；命令 frontmatter 增 `allowed-tools`/`argument-hint`/`arguments`(+`$name`/`$N`)。
- **为什么**：`disable-model-invocation` 直接省 token（不进清单）；`paths` 让技能按需激活；`context: fork` 让技能在分身里跑（省主上下文）；命令级 `allowed-tools` 让「/deploy 这类命令」自带工具白名单。
- **量**：2–3 天。

### P2-6 用量归因 / P2-7 上下文明细 / P2-8 丢弃旧工具结果

- **P2-6**：统计增加「来源维度」（工具调用 / 子代理 / 压缩 / 主动消息 / 定时任务），便于回答「钱花在哪」。1–2 天。
- **P2-7**：`/context` 等价物——把上下文占用拆成「系统提示 / 记忆 / 技能清单 / 历史 / 工具结果 / 摘要」，让用户知道谁在吃窗口。1 天。
- **P2-8**：压缩时优先丢弃「旧的工具结果」（保留结论与最近 N 条），比整体三段摘要更省且信息损失更小。1–2 天。
  **2026-10-10 核实（动手前必读）**：本项目的**工具结果从不进入持久化上下文**——
  ① `prompt/chatPipeline.js:20-23` 的 `buildHistory` 只保留 `user`/`assistant`；
  ② `chat/compaction.js:114-116` 的 `applyCompaction` 里 `meaningful` 过滤同样只留这两者（压缩本身就把工具消息全丢了）；
  ③ 聊天页的工具过程气泡是 `transient: true` + `pending: true` 的 UI 临时消息（`chat/useChatSend.js:277-287`，turn 结束即清），**不落库、不进请求**。
  所以「压缩时丢弃旧工具结果」在聊天页**没有可丢的东西**。真正吃窗口的是**同一个 turn 内的多轮工具循环**：`agent/loop.js` 把每轮的 `role:'tool'` 结果追加进本轮消息数组，之后每一轮都要重发一遍——那才是「旧工具结果」的所在。
  **改写后的做法**：在 `loop.js` 里把**较早轮次**的工具结果内容替换成占位标记，**保留消息本身**（`tool_call_id` 与前面 assistant 的 `tool_calls` 必须配对，删消息会被服务端拒），最近 N 条不动；纯函数可 Node 直测、接线只有一处。
  **2026-10-10 落地（`76ebe0e`，状态：✅ 已完成）**：纯函数落在 `agent/messages.js` 的 `elideOlderToolResults`（与 `serializeToolResult` 同处——都是「工具结果怎么变成历史文本」），接线只有 `loop.js` 每次请求前一处（含到轮次上限的强制收尾轮）。
  - 触发是**阈值制**：全部工具结果合计不超过 `TOOL_RESULT_ELISION_BUDGET`(24KB) 时**一条都不动**——没有收益就不丢信息；超了才动「比最近 `TOOL_RESULT_KEEP_ROUNDS`(2) 轮更早」的那些。
  - 只换 `content` 为 `TOOL_RESULT_ELIDED`（标记里写明「可重新调用工具取回」，别让模型以为内容还在别处）；**消息与 `tool_call_id` 一个不删**；比占位标记还短的结果不换（换过去反而更长）。
  - 返回新数组、不就地改消息对象：`runAgentTurn` 的 `history` 是调用方数组的浅拷贝，就地改会污染调用方的历史。
  - 选项 `toolResultKeepRounds` / `toolResultBudget` 可注入（默认走模块常量）。
  - 验收：`agentMessages` 7 条 + `agentLoop` 4 条行为测试；注入验证 11 条里 9 条变红（另 2 条是断言「不动」的负向对照）。
  - **未做（如实登记）**：子代理循环 `agent/subagent.js` 每轮同样重发工具结果（6 轮 × 8KB 上限），**没有**接这套省略。

## 6. 明确不做（防跑偏，沿用既有裁决 + 本报告新增理由）

**沿用既有裁决（本报告核实后同意，理由已更新）**

| 不做项 | 本报告补充理由 |
|---|---|
| LSP / 语言服务器 | 与既有裁决一致：Android 无 node 运行时。**替代路径**：P0-3 的 grep/glob 已能覆盖「找符号」的多数需求 |
| PTC（程序化工具调用） | 与 riskGate 双门架构冲突；Claude Code 也没有等价能力 |
| 生态市场 / 插件市场 | 与「不做多端/生态」一致；Claude Code 的 marketplace 依赖 git clone 与 shell（移动端不可行） |
| 任意 JS 插件 / hooks 执行脚本 | RN 无安全沙盒（进程内 eval 触达全部原生桥）——**Claude Code 的 5 种 handler 里 4 种依赖 shell/子进程，移动端不可移植**；保持声明式 JSON 是正确取舍 |
| 本地 git / JGit / 每 turn 自动建分支 | 与既有裁决一致；Claude Code 的 `isolation: worktree` 依赖 git 二进制 |
| 多端 / 桌面双栏 / Chrome 插件 / PPT 插件 / 消息树重构 / SQLite 全量迁移 / Annotate / Side Chat | 定位差异；Claude Code 的桌面/浏览器能力（内置浏览器、pane 弹出、computer use Desktop）在移动端无对应 |
| 多会话并行 turn | 移动端内存/电量；Claude Code 的并发 20 子代理与多会话并行是其桌面定位的产物 |
| fast mode | 服务端能力（同一 Opus 的快速配置），BYO 端点无对应 |
| auto 模式（分类器裁决权限） | RN 无分类器；且 easychat2 的「逐条确认 + 规则记忆」已覆盖安全需求 |
| 子代理 `permissionMode` | easychat2 的**只读名字白名单**是结构性保证，比「给子代理配权限模式」更难绕过——**不追** |
| 状态行 / 快捷键 / 终端 UI / fullscreen | 移动端不适用；Claude Code 的 statusLine 依赖 shell 脚本 |
| 技能 `` !`cmd` `` 动态注入 | 与「不做脚本执行」同源 |

## 8. 补充轮：会话 / 上下文 / 后台 / 成本 / 安全面的官方事实（第二轮抓取）

> 本节是第二批文档（`sessions`、`checkpointing`、`context-window`、`prompt-caching`、`agent-view`、`scheduled-tasks`、`headless`、`costs`、`security`、`monitoring-usage`、`how-claude-code-works`、`changelog` 418 版本）到位后对 §3 建议的**修正与加强**。逐条给「事实 → 对建议的影响」。

### 8.1 检查点语义（影响 P0-1 / P2-1）

**事实**：
- 触发：**你发送的每个开启新 turn 的 prompt 都创建检查点**；文件编辑前快照当前内容。
- 保留：**每会话最近 100 个检查点**的文件快照；丢弃旧检查点时**保留每个文件的第一个快照**（VS Code 用作 session diff 基线）。
- `/rewind` 菜单六项：**Restore code and conversation / Restore conversation / Restore code / Summarize from here / Summarize up to here / Never mind**。
- **不追踪**：Bash 命令改的文件（`rm`/`mv`/`cp`）、**除「前台 fork skill」外任何 subagent 的编辑**、Claude Code 之外或其它并发会话的改动、**symlink 与 hard link**（跳过并提示 `Restored the code, but skipped N files`）。
- 文档明写「**Not a replacement for version control**」。

**对建议的影响**：
1. **P0-1 的 UI 文案必须如实标注覆盖面**：easychat2 的 J1 快照同样只覆盖 `write_workspace_file`/`edit_workspace_file`（`writeTools.js:64-66,92-94`），**`run_shell` 改的文件不在内**。Claude Code 也这样——但它明确写在文档里。建议在「文件历史」入口加一行说明（仓库「不说假话」纪律），并在恢复后提示「已恢复 N 个文件；shell 命令改动的文件不在快照范围内」。
2. **P0-1 应顺手补「每个文件的第一个快照不被挤出」**：easychat2 现在 `HISTORY_MAX=200` 全局挤出（挤出前完整列表算删除，J1 已修 bug），但**没有「保留每文件首快照」语义** → 长跑工作区里，某文件的最早版本会被后续快照挤出，用户无法回到「最初」。Claude Code 的做法值得抄（成本极低：挤出时对每个 path 保留最旧一条）。
3. **P2-1（统一回退）的菜单形态可直接照抄**：六项菜单里 **「Restore conversation」与「Restore code」分开**——这正是 easychat2 现状（分支树 + 文件历史各自独立），而 **「Restore code and conversation」** 才是联动项。建议 P2-1 实现时**保留三个独立入口 + 一个联动项**，而不是把两个系统合并（避免 J 系担心的「强行合并互相掣肘」）。
4. **`/rewind` 的「Summarize from here / up to here」** 是「用压缩代替回退」的第三条路——easychat2 已有 `/compact`，可加「从这条消息往后压缩」的入口（成本低，收益中）。

### 8.2 压缩后的上下文重建表（影响 P0-5，并修正一处判断）

**事实（压缩后各类内容的下场）**：System prompt 与 output style 仍生效；**Project-root CLAUDE.md 与 unscoped rules 从磁盘重新注入**；auto memory 从磁盘重新注入；git status 重新读；plan 从磁盘重新注入；带 `paths:` 的 rules 按需重载；嵌套 CLAUDE.md 按需重载；**Claude 读过/改过的文件重读最多 5 个（按最近修改时间优先，超 5,000 tokens 只回路径引用）**；**已调用 skill 的正文重新注入，每 skill 上限 5,000 tokens、总计 25,000 tokens，超出先丢最旧**；后台命令与后台 subagent 继续运行并提醒 Claude；hooks 早先加入的上下文随对话被摘要。**skill 描述列表在 `/compact` 后不再注入**（只有实际调用过的 skill 正文保留）。

**对建议的影响**：
1. **修正**：我在 §2.8 说 easychat2「压缩是整体替换」→ 更准确的说法是：**easychat2 的系统提示是每轮从文件重建的**（`workspace/chat.js:77-111` 每轮直读 AGENTS.md / skills 清单 / 分身清单 / readLog），所以**压缩只替换消息历史，静态层天然不受影响**——这一点**比 Claude Code 的「压缩后靠重建」更彻底**（Claude Code 的 skill 描述列表压缩后就丢了，easychat2 下一轮又会注入）。应在报告中记为 ✅ 优势。
2. **P0-5 可加一条**：压缩时**保留「最近读过的文件路径清单」**（等价 Claude Code 的「重读最多 5 个文件」）。easychat2 的 `readLog`（30 条 LRU）已存在，压缩时把它写进摘要消息或系统提示即可——**成本极低、收益明显**（长会话里模型不会忘记自己在看哪些文件）。
3. **P0-5 再加一条**：`/compact` 后**重新注入已调用技能的正文**（Claude Code 有 5,000/25,000 token 预算）。easychat2 的 skills 是「清单 + 按需 read」，技能正文不进消息历史（模型每次 read），所以**不需要**——记 ✅ 已优。

### 8.3 提示缓存的 TTL / 失效 / 作用域（影响 P1-1）

**事实**：
- 两档 TTL：**5 分钟 / 1 小时**（1 小时写入按更高费率）。默认：Claude 订阅且在本计划额度内 → **主对话 1 小时**，「其它一切」（subagents / workflows / forks / compaction / session titles）**5 分钟**；用 usage credits / API key / 云厂商 → **全部 5 分钟**。
- 配置：`promptCacheTtl`（主对话）、`subagentPromptCacheTtl`（其它一切），只接受 `5m`/`1h`；禁用用 `DISABLE_PROMPT_CACHING[_HAIKU|_SONNET|_OPUS|_FABLE]`。
- **使缓存失效**：切模型、改 effort level、开 fast mode、连接/移除 MCP server、启停插件（提供 MCP server 的）、**deny 掉整个工具**（裸工具名/`Bash(*)`/工具名 glob）、**压缩对话**、图片/PDF 累积超限、升级版本。
- **保持缓存**：改仓库文件（只追加 `<system-reminder>`）、**会话中改 CLAUDE.md（不失效但也不生效，直到 `/clear`/`/compact`/重启）**、改权限模式、改 output style、调用 skills/commands、`/recap`、`/rewind`、spawn subagent。
- **作用域**：**限于一台机器 + 一个目录**（system prompt 内嵌 auto memory 路径、对话开头声明 working directory/platform/shell/OS）；同目录并行会话可互读。
- 观测：`/usage` 的 `Prompt cache (main)` 行（请求数/命中占比/miss 数/**last miss 可能原因**，如 `likely cause: tool definitions changed`）、statusline `prompt_cache` 对象、OTel cache read/creation tokens。
- 自定义 `ANTHROPIC_BASE_URL`/网关：是否生效取决于网关是否原样转发 `cache_control`（有的网关会丢弃标记导致**全量按未缓存计费**）。

**对建议的影响**：
1. **P1-1 升级为「P1-1 + 观测闭环」**：easychat2 已有 E1 的命中率显示，建议再补 **last-miss 原因**（Claude Code 给的是分类原因，如「工具定义变了」）——这能直接指导用户「别在会话中途改设置/加 MCP」。
2. **新增配置建议**：`promptCacheTtl`（5m/1h）——**注意费率**，默认建议 `5m`（BYO 端点多数不支持 1h，且 1h 写入更贵）；网关场景需在 UI 提示「你的网关可能不支持缓存标记」。
3. **重要提醒写进文档**：**压缩会使缓存失效**（Claude Code 明示）→ 这解释了「恢复旧会话时 `/compact` 最贵」；easychat2 的 85% 自动压缩同理 → 建议在自动压缩前**提示「本次压缩会让缓存失效、下一轮全量计费」**（或至少在统计里标注这次压缩的代价）。这与 E2 的「70% 提示条」正好可以合并展示。
4. **对 P0-6（ask 档）的交叉影响**：Claude Code 明确「**deny 掉整个工具**会使缓存失效，而**作用域规则（`Bash(rm *)`）与所有 allow/ask 规则不影响前缀**」→ easychat2 加 `ask` 档**不会**破坏缓存前缀（ask 属作用域规则），但**要避免**「按工具名 deny 整个工具」的用法被频繁切换（那是缓存失效点）。这条应写进 P0-6 的实现说明。

### 8.4 后台与调度的确切边界（影响 P1-8，并指出 easychat2 的一处优势）

**事实**：
- **后台 Bash/PowerShell 命令有时间限制**：`timeout` 配 `run_in_background`，**默认 30 分钟、最大 2 小时**，停止时通知 Claude；**v2.1.288 起该限制只作用于无人值守会话（`-p`/Agent SDK/CI/cloud），终端、桌面 app、VS Code 会话无限制**。
- **`/loop` 与 cron**：工具 `CronCreate`/`CronList`/`CronDelete`；**每会话最多 50 个 scheduled tasks**；调度器**每秒**检查、低优先级入队、在**你的 turn 之间**触发；按**本地时区**解释；有 jitter（重复任务固定延迟最长 30 分钟、整点半点的一次性任务最多提前 90 秒）；**重复任务创建后 7 天自动过期**；**只在 Claude Code 运行且空闲时触发**（关终端/退出会话即停）；**错过的触发不补**（忙时到期则在空闲时触发一次）；resume 恢复 `CronCreate` 任务，但**已过期重复任务与时间已过的一次性任务不恢复**、**自选间隔的 `/loop` 不恢复**。
- **后台会话**由 **supervisor 常驻服务**承载（每会话独立进程；`~/.claude/jobs/<id>/state.json`）；**未 attach 约 1 小时**停进程释放资源（`Ctrl+T` pin 可保活）；**机器关机即停**（睡眠可存活）；关机超 48 小时显示 stopped。
- **并发上限**：并发 subagents **默认 20**（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）；workflow 并发 **默认 16**（可调 1–256）；workflow 单次 `parallel()` 条目 **4,096**；单次运行 agent 总数 **1,000**；单 agent 重启 **最多 5 次**；一个会话 scheduled tasks **50**。

**对建议的影响**：
1. **P1-8 的边界更清楚了**：Claude Code 的后台命令有 30 分钟默认上限——**移动端更应如此**（电量）。建议 easychat2 的 `run_in_background` 也带**默认上限（如 10 分钟）+ 上限可调（最大 30 分钟）**，并在到点停止时通知模型（Claude Code 的做法）。
2. **easychat2 的定时任务有一处明确优势**：Claude Code 的 `/loop`「**错过的触发不补**」，而 easychat2 的定时 Agent 任务有 **6 小时宽限补跑**（`MISSING_RUN_GRACE_MS`，`tasks.js`）——移动端「App 大部分时间不在前台」，**补跑是必需**。这一点应写进文档，作为本地实现的正当性依据。
3. **并发上限建议做成配置**（与 P2-3 合并）：easychat2 现在子代理并发 2（`subagentTool.js:17`）。可参考 Claude Code 的分层上限，但移动端建议**保持保守默认（2）+ 允许调到 4**，并把「并发 N 个 agent 约等于 N 倍配额消耗」写进 UI 提示（Claude Code 明确写了这句）。
4. **调度语义需对齐一条**：Claude Code 明确「任务只在运行且空闲时触发」+「错过的触发不补」；easychat2 是「运行中触发 + 宽限补跑一次」。建议在定时任务面板把这两条**写清楚**（现有 `agentTask.notice.background` 已写「6 小时宽限补跑」，可再补「同一时刻只跑一个任务」）。

### 8.5 无人值守与 headless 契约（新增建议 P2-9）

**事实**：
- `-p` 契约：退出码 0/非零/SIGTERM **143**；管道 stdin 上限 **10MB**；`--output-format text|json|stream-json`；`--json-schema` 结构化输出；`json` 含 `total_cost_usd`（客户端估算）。
- **`--bare`**：跳过 hooks、skills、自定义命令、subagents、插件、MCP、auto memory 与 CLAUDE.md 自动发现；**不运行任何后台任务**（命令到超时就停，**不转后台**）；**从不读 OAuth 凭据或系统钥匙串**；需显式传上下文。
- **`--permission-prompts none`**（v2.1.259+）：无人值守时不咨询权限宿主、不等待；**会提示的一律拒绝**（除非 `PermissionRequest` hook 允许），并告诉模型没人能批准、不要重试；**移除需要人回答的工具**（如 `AskUserQuestion`）。
- `dontAsk` 模式：会提示的一律拒绝（适合锁死 CI）；`AskUserQuestion`、组织设为 `ask` 的 connector 工具、标 `requiresUserInteraction` 的 MCP 工具**即使有 allow 规则也被拒**。

**对建议的影响**：
- **新增 P2-9「无人值守模式」**：easychat2 已有等价纪律（无 `confirm` 钩子 → 需确认工具一律拒绝，`registry.js:158-164`；定时任务不接审批钩子 → 需确认工具被拒），但**没有把它做成显式模式**。建议：定时 Agent 任务 / 未来的后台命令场景引入显式「无人值守」标记，在该模式下：
  1. 需确认工具一律拒绝（现状 ✅，但要显式化并写进提示词让模型别重试）；
  2. **不注册需要人回答的工具**（未来的 `ask_user`，P1-6 必须在此模式下自动摘除——Claude Code 就是这么做的）；
  3. 允许的工具子集**显式收窄**（建议：只读 + 无外发，或按任务配置）；
  4. 完成后把「因无人值守被拒绝的操作」列进结果，让用户知道发生了什么。
- 量：1 天（纯策略 + 提示词 + 面板提示）。

### 8.6 成本与用量（新增建议 P2-10）

**事实**：
- `/usage` Session 块按**本地 token 计数 × 列表价**；**总计在 `/clear` 开新会话时重置**；`Prompt cache (main)` 行含 miss 原因；套餐用量按 **skills / subagents / plugins / 各 MCP server** 归因；**`Loops` 行**列出最近最重的 `/loop` 或其它 scheduled task（触发频率、运行次数、总/单次 token、最后运行时间）。
- `/insights`：分析本机最近会话，写 HTML 到 `~/.claude/usage-data/report.html`（**单次最多分析 200 个未见过的会话**），报告按 `cleanupPeriodDays` 删除。
- **后台 token 消耗**：即使空闲也消耗（会话摘要、命令处理），**typically under $0.04 per session**；prompt suggestions 复用会话缓存。
- **长会话攀升原因**：长上下文（每次请求发全量）、缓存 miss、scheduled tasks 空闲仍按间隔触发、跨会话消息、**goal check-ins（每个 goal 在你的 prompt 之间最多 3 次空闲 check-in）**、subagents/workflows 各自发请求、agent teammates 持续消耗、**压缩本身是一次大请求**（`/clear` 零成本）。
- **减量建议（文档原样要点）**：主动管理上下文（`/clear` 切任务、`/compact Focus on code samples and API usage`、CLAUDE.md 写 `# Compact instructions`）；**subagent 可 `model: haiku`**；优先 CLI 工具而非 MCP；**把专门指令从 CLAUDE.md 移到 skills**（CLAUDE.md 目标 200 行内）；调整 thinking；把啰嗦操作交给 subagents。

**对建议的影响**：
- **新增 P2-10「用量归因 + 成本提示」**（把原 P2-6 扩展）：
  1. 统计面板加「**定时任务/主动消息消耗**」一行（对应 Claude Code 的 `Loops` 行）——用户能知道「后台定时任务每月花掉多少」；
  2. 加「**缓存 miss 原因**」（对应 `Prompt cache (main)` 的 last miss cause）；
  3. 加「**压缩代价**」提示（压缩前后 token 对比）；
  4. **`/insights` 式本地报告**（可选）：把本机会话历史汇总成一份可分享的报告（HTML/Markdown），用于自查用量结构。
- 量：1–2 天（前三条）；报告式分析另计。

### 8.7 审计事件面（新增建议 P1-12）

**事实**：Claude Code 的 OTel 事件面覆盖 **40 个事件**，其中与「谁做了什么、被谁拦了」直接相关的审计映射为：

| 审计目标 | 事件 | 关键属性 |
|---|---|---|
| 工具调用允许/拒绝及来源 | `tool_decision` | `decision`、`source`、`tool_name`、`tool_parameters` |
| 权限模式升级 | `permission_mode_changed` | `from_mode`、`to_mode`、`trigger` |
| 策略 hook 阻止动作 | `hook_execution_complete` | `hook_event`、`num_blocking` |
| 登录/登出/认证失败 | `auth` | `action`、`success`、`error_category` |
| MCP server 连接或失败 | `mcp_server_connection` | `status`、`server_name`、`is_plugin`、`error_code` |
| 插件安装及来源 | `plugin_installed` | `plugin.name`、`marketplace.*` |
| 执行的命令与触及的文件 | `tool_result` / `tool_decision` | 需 `OTEL_LOG_TOOL_DETAILS=1` |
| 压缩发生 | `compaction` | — |
| 子代理完成 | `subagent_completed` | — |

文档明确：**Claude Code 只发原始事件流**，异常检测/基线/跨会话关联/告警由你的后端负责。

**对建议的影响**：
- **新增 P1-12「审计事件面补齐」**：easychat2 的 E4 事件流目前只挂 `user`/`assistant`/`tool_call` 三类事实（`sessionEvents.js:19-22` 共 8 种类型）。建议补齐**权限与策略维度**：
  1. `tool_decision`（工具名 + allow/deny/ask + 来源：规则/弹框/hook/默认）；
  2. `permission_mode_changed`（ask/read/write 切换 + 触发点）；
  3. `hook_blocked`（哪个 hook 事件拦了什么，对应 `num_blocking`）；
  4. `compaction`（压缩前后消息数/token 估算）；
  5. `subagent_completed`（分身名 + 轮次 + 结论长度）；
  6. `mcp_server_connection`（连接成功/失败 + 错误码）。
- 为什么值得做：E4 的定位就是「旁路审计」（只写不回读、写失败静默），补这几类**几乎零成本**（都是既有流程里顺手 emit），但把「事后排查」从「只有消息流」提升到「能回答『这次为什么被拦了』」。与 §2.5 的「无来源标签」缺口正好互补。
- 量：1 天（事件类型 + 埋点 + 导出文案）。

### 8.8 安全事实对照（修正一处、加强一处）

| Claude Code 事实 | easychat2 对照 | 结论 |
|---|---|---|
| **Working directory boundary 只是权限提示**——「你批准的 Bash 命令仍可写到你的用户账户能写的任何地方」；要 OS 级限制必须开 sandboxing | easychat2 的沙盒是**应用私有目录**（`<documentDirectory>/workspace/<sandboxId>/`），`run_shell` 的 cwd 被限制在沙盒内且路径经 `sanitizeShellCwd` 逃逸防护；SAF 外部根下 shell **直接禁用** | ✅ **easychat2 更强**（应用私有沙盒是 Android 强制的，不依赖用户信任） |
| **workspace trust**：仓库 `.claude/settings.json` 的 allow 规则与 `additionalDirectories` 需信任该目录后才生效，**deny/ask 立即生效**；`-p` 会话不显示该对话框；home 目录启动的信任只对当次会话有效 | 无信任概念（无「他人提交的配置」场景）——**但 P1-2（工作区级设置）会引入这个场景** | ❗**P1-2 必须照抄这条信任模型**：工作区文件里的「收紧类」设置立即生效，「放宽类」（模式提到 write、开 shell、加附加目录）**必须显式信任后才生效** |
| **Windows WebDAV 风险**：启用 WebDAV 可能让 Claude Code 触发对远程主机的网络请求，**绕过权限系统** | 不适用（无 Windows 桌面版） | ⛔ 不适用 |
| **WebFetch 会对页面跑一次独立模型调用**，Claude 收到那次调用的答案而非原始页面（反注入） | 无 `web_fetch`（P0-2 待做） | ⚠️ **P0-2 应照抄这条**：抓取的网页内容**先经一次独立的摘要/抽取调用**再进主上下文——这既是反提示注入，也顺便解决「正文太长」 |
| **网络命令审批**：`curl`/`wget` 默认不自动批准；deny 规则**按命令字面**匹配；要网络强制隔离用 sandbox | `run_shell` 每次需确认（更严）；无网络隔离 | ✅ 已对齐（更保守） |
| **凭据存储**：macOS Keychain / Linux `0600` 文件 / Windows 用户 ACL 文件 | expo-secure-store（Android Keystore / iOS Keychain） | ✅ 已对齐 |
| **MCP**：Anthropic **不审计也不管理任何 MCP server**；插件也能加 server（所以审查 `.mcp.json` 看不到全部） | 第三方默认 CONFIRM + 硬禁 + 执行层复查；服务器列表在应用设置里可见 | ✅ **更可控**（至少用户能看到全部服务器） |
