# 需求文档：语音消息

## 简介

新增语音消息能力，替换原「打电话（WebRTC + 信令）」规划：

- **用户发语音**：录音后转写为文字进入上下文；转写优先复用现有聊天 API 配置的 `/audio/transcriptions`，失败时引导用户可选补配独立转写服务，再失败则存占位文本。
- **角色回语音**：复用既有 TTS 能力，按角色卡设置决定「显示原文」或「纯语音」。
- **音频落盘**：用户与角色的语音音频保存到本机文件，随消息可回放。

全链路为纯前端，不引入自建后端，不引入 WebRTC。

## 术语表

- **STT（Speech To Text）**：语音转文字。
- **转写配置（Transcription Config）**：调用 `/audio/transcriptions` 所需的地址、密钥与模型。
- **复用转写（Reused Transcription）**：直接使用用户当前聊天 API 配置的 `baseUrl` / `apiKey` 调转写端点。
- **独立转写（Dedicated Transcription）**：用户在设置页单独填写的转写服务配置。
- **语音形态（Voice Display）**：角色卡字段，决定角色回复是否显示原文。
- **语音消息（Voice Message）**：`kind: 'voice'` 的消息，包含转写/原文文本与音频引用。

## 需求

### 需求 1：用户发语音

**用户故事：** 作为用户，我希望用语音代替打字发送消息，以便更快表达。

#### 验收标准

1. 输入区应提供语音入口，用户按住录音、松开结束。
2. 系统应在录音前申请麦克风权限；未授权时给出可读提示且不启动录音。
3. 当录音结束且转写成功时，系统应以转写文本作为该条用户消息的文本并进入上下文。
4. 当录音结束且转写失败时，系统应按需求 3 的回退顺序处理。
5. 系统应限制单条语音的最短与最长时长，超出范围时给出提示并丢弃。
6. 系统应在录音期间给出进行中的视觉反馈。

### 需求 2：语音消息展示与回放

**用户故事：** 作为用户，我希望语音消息像图片一样可回放，以便重新听清内容。

#### 验收标准

1. 语音消息应以带时长与播放控件的语音气泡展示。
2. 当用户点击播放时，系统应播放该条语音音频。
3. 系统应将录音与角色语音音频保存到 `documentDirectory/voice/`，并在消息中记录引用。
4. 当消息或会话被删除时，系统应回收不再被任何会话或待发送项引用的语音文件。
5. 系统应在音频文件缺失或损坏时给出可读提示，不阻断聊天。

### 需求 3：转写配置的回退顺序

**用户故事：** 作为用户，我希望不必额外配置就能用语音，只有当前来源不支持时才需要补配。

#### 验收标准

1. 当用户使用默认配置发送语音时，系统应优先用当前聊天 API 配置的 `baseUrl` / `apiKey` 调用 `POST {baseUrl}/audio/transcriptions`。
2. 当复用转写返回「端点不存在或不支持转写」时，系统应提示当前来源不支持语音转写，并引导用户到设置页填写独立的转写配置。
3. 当用户已配置独立转写服务时，系统应改用它转写。
4. 当复用转写与独立转写均不可用时，系统应把该条语音存为占位文本 `[用户发来一段语音]`，不阻断发送。
5. 系统应在当前会话内记住「当前来源是否支持转写」的判定，避免每条语音重复触发必然失败的请求。
6. 系统应在功能说明中明确：转写会将音频上传到所选服务商。

### 需求 4：转写配置存储

**用户故事：** 作为用户，我希望像 TTS 一样集中配置转写服务。

#### 验收标准

1. 设置页应提供「语音转文字」配置入口。
2. 系统应支持填写转写服务的名称、接口地址、密钥与模型，模型默认 `whisper-1`。
3. 系统应支持新增、编辑与删除转写配置，并选择当前使用的配置。
4. 系统应将转写密钥保存在本机（走密钥保险箱），不硬编码、不写入文档。
5. 系统应支持「不使用独立配置（仅复用当前聊天来源）」这一默认状态。

### 需求 5：角色按角色卡回语音

**用户故事：** 作为用户，我希望不同角色可以有不同的语音呈现方式。

#### 验收标准

1. 角色卡应提供语音形态字段，取值包含「仅文字（默认）」「语音 + 原文」「纯语音」。
2. 当语音形态为「仅文字」时，系统行为与现状一致，不自动发声。
3. 当语音形态为「语音 + 原文」时，系统应在助手回复后合成语音并展示原文与语音气泡。
4. 当语音形态为「纯语音」时，系统应展示语音气泡且隐藏正文，但正文仍入库并进入上下文与记忆。
5. 系统应在 TTS 未配置或合成失败时降级为仅文字，不阻断回复。

### 需求 6：模型能力标记

**用户故事：** 作为用户，我希望能标注当前来源是否支持语音识别。

#### 验收标准

1. 系统应在「确认模型能力」弹窗中提供「支持语音识别」开关。
2. 当来源标记支持语音识别时，系统应允许把音频作为多模态内容直接发送作为兜底路径。
3. 系统应把该能力纳入 API 配置指纹校验。

### 需求 7：与既有约束一致

#### 验收标准

1. 系统应放开 Android 的 `RECORD_AUDIO` 权限（移除 `blockedPermissions` 中的该项）并保留其余权限限制。
2. 系统应保证转写与合成失败不写入消息记录、不污染错误文本。
3. 系统应保持 `pending` 占位消息不落盘的既有约束。

## 非目标

- 不做端侧转写（列入后续阶段，作为离线兜底）。
- 不做 WebRTC 实时通话与信令服务。
- 不做历史语音音频的重新回传（历史语音只以文本或占位进入上下文）。
