# G 系设计要点（推送删除安全）

> 做决定的地方：每条写明「为什么这样做、为什么不另一种」。状态：G1–G3 完成（c1009c24）。

## 核心问题：三态 vs 二态

推送 diff 的三种文件状态，原实现只认两种：

| 状态 | 原实现 | G1 修复后 |
|---|---|---|
| 远程有 + 本地有 + 同 sha | 未改（沿用远程 sha） | 同 |
| 远程有 + 本地有 + 异 sha | modified | 同 |
| 远程无 + 本地有 | added | 同 |
| **远程有 + 本地曾经有、现在没有** | **removed（真删除）** | removed（真删除）|
| **远程有 + 本地从未有过**（拉取跳过的二进制/超大） | **removed ← BUG！** | **原样传递** |

第三态（「从未物化」）的证据只能来自**基线快照**——`setRepoSnapshot` 在拉取/推送
成功后写入的本地清单。关键性质：**被跳过的文件从不在基线里**（基线记录的是实际
落盘的文件），所以「远程有 ∧ 基线有 ∧ 本地无」精确等于「曾经物化过而现在没了」。

## 为什么 knownPaths 由宿主注入而不是 repoPush 自己读

`storage/workspace.js` 依赖 AsyncStorage → 会把 expo 原生模块拖进 repoPush 的
模块图，破坏它的纯 Node 可测性（与 subagent.js 的惰性 require 同款教训）。
分层原则：**repoPush 是纯逻辑 + fetch 注入；存储由宿主（GithubPanel）读好传入**。

## 为什么无基线时 removed 恒空（而不是「按本地全集删」）

两种坏可能：误删（把从未拉过的远端文件当删除）vs 漏删（用户真删了但基线丢了，
远端留着）。**数据的不可逆性决定了两者不对称**：漏删可以再删一次（远端文件还在），
误删需要从 git 历史考古恢复。所以 fail-safe 选「宁可少删」：无基线 → removed 空；
推送成功后宿主刷新基线，下一次推送即恢复完整删除语义。

## 为什么读不全的文件不参与推送（而不是推截断版）

`readWorkspaceFile` 默认 maxChars=1MB：>1MB 文件原实现会被读成前 1MB，sha 与远程
不符 → 判 modified → **把半截文件推上去**（静默数据损失，比误删更隐蔽——误删至少
在确认框里列出来）。修复：显式传 8MB（宽于文本线 5MB）+ `truncated` 记账——
读不全就不动它，如实提示「N 个文件过大未参与同步」。

## G3 为什么放宽文本线（5MB）而不是只做「清单标注 + 重拉入口」

任务书给的两个选项，选前者的依据（逐条核对过）：
- 落盘侧无限制（writeAsStringAsync 直写，仅受 200MB 总量约束）；
- 读取侧 1MB 只是预览默认——offset 分页是为大文件设计的，落盘比分页更基础；
- 推送侧上限已随 G1 修复（8MB），不会推截断版；
- 编辑侧 4MB 拒绝线存在且如实拒绝（不改它——编辑一次读全文，4MB 已到手机内存的
  合理边界）。
代价：解压时单文件峰值 5MB string（zip 整包本就 6MB 在内存，同量级）。

## 清单文件为什么覆盖式单文件（而不是 append 或按分支分文件）

`pull-skipped.json` 语义 = 「**最近一次拉取**跳过了什么」，覆盖写最贴合语义；
与 `pull-manifest.json` 同域同风格（`.easychat/` 下点目录，文件管理器日常不干扰）。
agent 读它即知道「仓库里还有哪些文件不在本地」——这是 G1 修复之外的第二层价值：
模型不再对「文件不存在」给出错误结论（例如「仓库里没有图标」）。

## 与分支系统的无关性

G 系全部改动在「本地副本 ↔ 远程树」同步链路，不触碰对话/分支/事件流。
