# 需求文档：群聊情境感知

## 简介

改造群聊回复的请求构造方式。当前群聊是「把同一条用户消息分别交给多个角色，各自按一对一场景回复」，角色本身并不知道自己身处群聊、旁边还有其他角色。本次改造让每个发言角色的提示词都包含群聊情境：它知道自己在一个多人环境中，知道在场有哪些角色，并能看到最近群聊里其他角色的发言。

## 术语表

- **群聊情境**：注入到发言角色提示词中的独立 system 段，说明这是多人群聊、列出在场成员、说明还有其他角色会发言。
- **在场成员**：当前群聊会话的全部角色成员。
- **共享群聊历史**：同一份群聊对话记录，对所有角色一致，仅各角色的自我认知不同。
- **自我认知**：提示词中「我是谁」，即当前发言角色的身份。

## 需求

### 需求 1：注入群聊情境

**用户故事：** 作为用户，我希望群聊里每个角色都知道自己在群聊中，而不是以为在和用户一对一聊天。

#### 验收标准

1. 当构造群聊发言请求时，系统应为发言角色追加独立的 system 段 `[群聊情境]`。
2. `[群聊情境]` 应说明当前处于多人群聊环境，并列出全部在场成员及其简介。
3. `[群聊情境]` 应说明除自己以外的其他在场角色也会发言。
4. `[群聊情境]` 应描述当前发言角色自身在当前环境中的所见所闻所感（在场成员与最近群聊对话）。

### 需求 2：共享群聊历史与自我认知

#### 验收标准

1. 所有发言角色应看到同一份群聊历史记录。
2. 群聊历史应标注每条发言的说话者，使用户与其他角色的发言可区分。
3. 每个发言角色的提示词应仅替换「我是谁」部分，即系统段中的角色名与角色卡设定为当前发言角色自身。
4. 当同一轮内有多个角色发言时，后发言的角色应能看到同轮前述角色的发言。

### 需求 3：在场成员与最近对话

#### 验收标准

1. `[群聊情境]` 应包含全部在场成员名单，含各成员名称与简短简介。
2. `[群聊情境]` 应包含最近若干条群聊对话，并标注每条发言的说话者。
3. 当群聊历史为空时，`[群聊情境]` 应仅包含在场成员信息，不出现空的历史区块。

### 需求 4：成员人设卡的懒生成与缓存

**用户故事：** 作为用户，我希望即使某个角色卡没有简介或简介写得很随意，群聊里的其他角色也能通过一句话了解它的大致人设。

#### 验收标准

1. 系统应以成员角色卡的 `description` 与 `personality` 拼接后去除空白，字符数低于 30 视为「简介不足」。
2. 当发言角色需要了解某个简介不足的在场成员时，系统应调用一次 LLM，基于该成员的完整角色卡生成 1-2 行第三人称简介（人设卡）。
3. 系统应将生成结果按成员 id 缓存在群聊会话中，同一成员不重复生成。
4. 当成员已有人设卡缓存时，系统应直接复用，不再触发调用。
5. 当 LLM 生成失败时，系统应回退为代表该成员名称的占位简介，不阻塞群聊请求。

### 需求 5：成员最近发言

#### 验收标准

1. `[群聊情境]` 中每个成员应附带其最近若干条发言摘录，并标注文本。
2. 当某成员尚无发言时，系统应仅展示该成员简介，不出现空的发言区块。
3. 成员最近发言的提取不应触发额外的 LLM 调用。

### 需求 6：不改变既有单聊行为

#### 验收标准

1. 当会话为单聊时，请求构造应与改造前一致，不注入 `[群聊情境]`。
2. 系统应保留发言角色各自的 systemPrompt、worldInfo 与 regexScripts 处理流程。
3. 系统应保留全局预设、用户人设与记忆摘要的注入顺序。
