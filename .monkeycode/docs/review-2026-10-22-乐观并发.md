## ① 回退兼容性：改了索引格式，旧版 App 会怎样

### 事实

`d43470cb` 把角色库索引从纯数组 `["id1","id2"]` 改为对象 `{ ids, revision }`
（`src/storage/characters/index.js:59-89`）。

旧版（修复前）的 `readCharacterIndex` 判定逻辑是：

```js
if (stored.status === 'ok' && Array.isArray(stored.value)) → 正常
else corrupt = (status === 'corrupt') || (status === 'ok' && !Array.isArray(value))
```

### 实测结果

直接跑旧版判定逻辑读新格式：**`{ ids: null, corrupt: true }`**。

即旧版会把新格式索引判成损坏，走 `index.corrupt` 分支
（`index.js:370-385`）：`backupCorruptValue(索引)` → `rebuildCharacterItemsFromKeys()`。

### 会不会丢卡：不会

`rebuildCharacterItemsFromKeys`（`index.js:188-212`）只做一件事——扫出所有
`character_item::` 前缀键，逐条解析。**它完全不读索引**（已用源码断言核实：
该函数体内不含 `CHARACTER_INDEX_KEY`）。

角色卡正文本来就按 id 独立存储（当初为绕开 Android SQLite 单值 2MB 上限而拆键），
所以索引格式与卡片数据无关，重建能全部捞回。实测 3/3 全回。

### 代价（不丢数据，但有一次性开销）

1. 多写一份索引备份（`backupCorruptValue`）
2. 首次启动多一次全键扫描
3. `revision` 归零，此前累积的版本号丢失

### 结论

**回退安全**，不需要为兼容旧版改代码。若将来要做，可选方案是「双格式写」
（同时写 `ids` 数组到另一个键，供旧版读），但那是为不存在的需求增加复杂度——
用户不装旧版 APK 就不会触发。

## ② `revision === null`（索引损坏）时跳过校验，是否安全

### 事实

- `getCharacterLibraryRevision()` 在 `corrupt` 时返回 `null`（`index.js:113-116`）
- `persistLibrary` 的校验条件含 `!index.corrupt`（`index.js:226-233`），损坏时直接跳过
- 调用方（`characterLibraryPersistence.js:62`、`charactersTools.js:176`）见到 `null`
  就传 `undefined`，即「不做校验」

### 为什么这样设计是正确的

把「不知道版本」当成「版本 0」会造成一长串假冲突——索引损坏时版本号本身没有意义，
强行比对只会让每次写都失败。所以选择「跳过」而不是「硬比」。

### 跳过是否留下数据风险

索引损坏 → 重建 → `needsPersist = true` → `persistLibrary(list)`（`index.js:425-431`）。
这一句**没有传 `expectedRevision`**，是**有意的**：

- 此时 `list` 是刚刚扫完全部键得出的结果，它就是当前唯一真相，没有「旧快照」概念
- 该窗口内不存在另一个基于旧快照的写入方（读函数同步串行完成重建与写回）

并且写失败会 `setCharacterLibraryWriteBlocked(true)`（`index.js:429`），
后续任何写都会被写闸挡住，不会带着不一致的索引继续跑。

### 残留窗口（如实记录，低危）

`persistLibrary` 是「读索引算 currentRevision → 一系列 await → 写索引」的结构
（`index.js:221-257`）。如果两个写入方**都不带 `expectedRevision`**
（即都跳过校验），理论上仍可能互相覆盖 —— 但当前所有关键写入方
（AppContext 的 6 处变更、MCP 的 `mutateLibrary`）都已带版本号，
剩下不带的是内部维护路径（重建写回、启动时的头像/人设补写），
它们都在「刚读完库」的同一上下文里，不存在旧快照问题。

**结论**：可接受。若要彻底消除，需要在存储层加互斥锁（串行化整个
read-modify-write），收益不抵复杂度。
